# 디자인 산출물 ↔ 데이터 불일치

구현 전에 정리해야 할 항목. 발견 시점: 목 데이터 작성 중.

## 1. DECREE 37/2026의 영향 제품 수 — S2와 S3가 어긋난다

| 위치 | 표기 |
|---|---|
| S2 Laws 목록 | `제품 4` |
| S3 Law Detail | `AFFECTED — 3` |

**판단: 4가 맞다.** 라벨 표시 규정은 사전포장 식품 전 품목에 적용되므로 유자청(HS 2007.99)도 해당된다. 제외할 근거가 없다.

**조치**: `seed/data/laws.json`의 `VN-2026-037.affectedProductIds`를 4개로 확정했다.
구현 시 **S3의 섹션 라벨을 `AFFECTED — 4`로 고치고 제품 행을 4개로** 만든다. 유자청은 `impact: "low"`.

이 수치는 하드코딩하지 말고 `law.affectedProductIds.length`에서 뽑는다. 그러면 같은 종류의 어긋남이 다시 생기지 않는다.

## 2. CIRCULAR 29/2023은 제품 3개가 맞다

영양성분 표시 의무는 사전포장 가공식품 대상이고, 유자청은 단순 과실 가공품으로 제외했다. S2 표기 `제품 3`과 일치한다. **조치 없음.**

## 3. 지오그래피 렌더링 미확인

`design/neo-dots.js`는 Claude Design 런타임에서 실행된다. 로컬 정적 렌더에서는 캔버스가 비어 나온다.
S1 지구본과 S5 지도의 실제 렌더 결과를 캔버스에서 확인하지 못했다. 포팅(build-plan §10 8단계) 시 시각 결과를 처음으로 검증하게 된다.

## 4. 모든 수치는 파생값으로

디자인에 박혀 있는 숫자들 — `대응 필요 3건`, `MUST DO — 4`, `PRIORITIES — 3`, `PRODUCTS — 4`, `읽지 않음 3`, `규제 5 · 미완 액션 10` — 은 **전부 데이터에서 계산**한다. 문자열로 박으면 localStorage 상태가 바뀔 때 즉시 거짓말이 된다.

`규제 5 · 미완 액션 10` 검산: 법률 5건, 전체 액션 9건. **10이 아니라 9다.**
→ 이것도 파생값으로 처리하면 자동으로 맞는다.

# 판정 — 4단계 완료 시점 (S1 Home)

Claude Code가 올린 7건과 판단 3건에 대한 확정. **이 판정이 계획서보다 우선한다.**

## 판단 3건 — 전부 승인

**shadcn init 되돌림.** 옳다. `--accent: oklch(0.97 0 0)`가 들어왔다면 시안이 흰색이 되어 전 화면이 무너졌다. `--radius: 0.625rem`는 규칙 2 위반이고, 흰 배경 `@layer base`와 `.dark` 블록은 단일 테마 결정과 충돌한다.

**단, 9단계 Drawer는 `npx shadcn add drawer`로 받지 말 것.** 같은 오염이 재발한다. `npm i vaul` 후 래퍼를 직접 쓴다. 40줄이면 되고, `border-radius: 0`을 강제해야 하므로 어차피 손을 봐야 한다.

**Pretendard 자체 호스팅.** 옳다. 400/500/700만 쓰는데 가변폰트 2.06MB는 낭비다.

**Next.js 16 + Turbopack.** 11단계에서 Serwist를 시도하지 말고 **서비스워커를 직접 쓴다.** 우리가 필요한 건 정적 자산 precache와 JSON 7개 + geo 1개의 stale-while-revalidate뿐이다. 60줄이면 끝나고 번들러에 묶이지 않는다. Serwist를 넣으면 Turbopack 호환성 문제를 떠안는 대가로 쓰지도 않을 기능을 받는다. 단순함이 먼저다.

## 7건 판정

**1. S2 행 92px — 승인.** `--row-law: 92px` 유지. 계획서의 3종이 틀렸고 원본이 맞다.

**2. 탭바 가운데 정렬 — 승인.** 규칙 문구를 고친다: *"화면 콘텐츠는 전부 좌측 정렬. 탭바와 시트 드래그 핸들은 예외."*

**3. 상태 스트립 gap:12 — 반려. 14로 정규화한다.**
원본이 진실이라는 원칙의 예외다. 2px 차이는 아무도 지각하지 못하는데 매직 넘버는 영구히 남는다. 의도된 값이라는 근거가 없고, 나머지 모든 행이 14다. 시스템 무결성이 이긴다.

**4. 액션 문구는 데이터를 따른다 — 승인.**
S1↔S3가 같은 레코드를 가리켜야 6단계 공유 스토어가 성립한다. 문구 통일은 필수다.

**추가 확인 필요**: 데이터 문구가 원본보다 길다. 390px에서 `--row-action: 66px` 안에 한 줄로 들어가는지 렌더로 확인할 것. 넘치면 데이터 문구를 줄인다 — 데이터는 우리 것이고 행 높이는 원본 값이다.

**5. S6 EARLIER 날짜 — 승인.** 기준일보다 미래인 날짜는 원본 오기다. 데이터가 맞다.

**6. 체크박스 체크 상태 `--accent` 채움 + `--on-color` ✓ — 승인.**
원본이 박스 안에 `700 10px/1 · color:#171717`을 예약해둔 것은 색면 채움의 명백한 증거다. 근거가 좋다.

시안을 쓴 것도 맞다. 이 앱의 긍정·활성 계열은 시안 하나다 — 활성 탭, 링크, `施` 마커, CTA가 전부 시안이다. 체크박스가 여기 합류하는 게 자연스럽다. 초록 `--risk-low`는 S6 '액션 완료' 알림 유형 전용으로 남긴다. 둘을 섞으면 의미가 흐려진다.

**7. D-Day 배지 색 경계 — 30일 단일 컷을 3단으로 교체한다.**

원본의 확정점은 둘이다. D-14 = critical, D-45 = medium. 30일 컷은 두 점을 만족시키지만 `--risk-high`를 D-Day에서 영영 쓰지 않게 만든다.

```
기한 경과 또는 D-14 이하  →  --risk-critical
D-15 ~ D-30              →  --risk-high
D-31 이상                →  --risk-medium
deadline === null        →  배지 없음
```

두 확정점을 그대로 통과하고 4색 중 3색을 쓴다. 초록은 D-Day에 쓰지 않는다 — 마감일 배지가 "안전"으로 읽히면 안 된다. `DECREE 15/2018`처럼 `deadline`이 없으면 배지 자체를 그리지 않는다(원본과 일치).

## 새로 발견된 것 — 한자 마커의 플랫폼 편차

**施 留 豫가 Pretendard 서브셋에 없다**는 확인은 중요하다. serif 폴백이 실제로 동작한다는 뜻이지만, **어느 serif로 떨어질지는 기기마다 다르다.** Windows는 바탕, macOS·iOS는 다른 명조, Android는 또 다르다. 이 앱의 서명 요소가 기기마다 다른 골격으로 찍힌다.

**조치: Noto Serif KR에서 이 세 글자만 서브셋해 자체 호스팅한다.** 3글자면 2~4KB다.

```css
@font-face {
  font-family: 'NEO Mark';
  src: url('/fonts/neo-mark-subset.woff2') format('woff2');
  unicode-range: U+65BD, U+7559, U+8C6B;  /* 施 留 豫 */
  font-display: block;
}
.t-mark { font: 700 12px/1 'NEO Mark', Pretendard, serif; }
```

`font-display: block`을 쓰는 이유 — 마커가 폴백으로 잠깐 찍혔다가 바뀌면 눈에 띈다. 3글자짜리 파일이라 로드는 즉시다.

# 7단계에서 발견 — S4·S6 아트보드 ↔ 데이터

아트보드가 목 데이터보다 먼저 만들어져 숫자가 어긋나 있다.
§4의 원칙대로 **전부 데이터에서 계산**하고 아트보드 숫자는 버린다.

## 5. S4 우선순위 타일 수치

| 타일 | 아트보드 | 데이터 파생 |
|---|---|---|
| 라벨링·표시 | 법률 3 · 미완 5 | **법률 2 · 미완 6** |
| 식품안전·인증 | 법률 2 · 미완 2 | **법률 2 · 미완 0** |
| 포장·환경 | 법률 1 · 미완 3 | 법률 1 · 미완 3 (일치) |

법률 수는 `law.category` 매칭, 미완은 그 법률들의 미완 액션 합이다.
labeling = VN-2026-037(액션 4) + VN-2023-029(액션 2) = 법률 2 · 미완 6.
safety = VN-2026-046 + VN-2018-015, 둘 다 액션이 없어 미완 0.

**위험도는 아트보드와 일치한다** — HIGH / MEDIUM / CRITICAL.
해당 category 법률 중 최대 위험도이고, 라벨과 상단 4px 바가 같이 이 값을 쓴다.

| 조미김 | 법률 3 | **법률 5** |

어느 규칙으로도 #E0A800이 나오지 않는다.

# 9단계 판정 — S5 Map

아트보드가 목 데이터보다 먼저 그려져 어긋난 지점, 그리고 명세가 비워둔 자리를 여기서 닫는다.

## 9. 점 색 — S1과 S5가 다르다

8단계에서 `DotGeo`의 `dotColor` 기본값을 `--text-3`로 두고 남겨둔 질문이다.
**S5는 `dotColor="var(--geo-dot)"`를 넘긴다. `DotGeo`의 기본값은 건드리지 않는다.**

S1 지구본은 전경 히어로라 `--text-3`(#6B6B6B)로 또렷해야 하고, S5 지도는 시트 뒤에
깔리는 배경이라 `--geo-dot`(#3A3A3A)로 물러나야 한다. 아트보드도 S5에만
`dot-color="#3A3A3A"`를 넘기고 S1에는 넘기지 않는다.

## 10. 지도는 전체화면 배경이 아니다

design-prompts §S5의 "전체화면 SVG 점지도"는 아트보드와 어긋난다. 아트보드는 330×366 박스를
`top:60px; right:-36px`으로 우측 밖으로 흘린다 — S1 지구본과 정확히 같은 어법이다.
같은 문서가 "S1처럼 우측 밖으로 흘려 좌측에 여백을 남긴다"고도 적었으니, "전체화면"이 헐거운 말이다.

`Screen`이 상단 44px을 이미 잡으므로 콘텐츠 좌표로 환산해 `top:16px; right:-36px`이 된다.
실측: 지도 좌측에 96px 여백이 남고 우측 36px이 프레임 밖으로 잘려 나간다.
**가운데 정렬하지 않는다. 비대칭이 의도다.**

## 11. 시트 높이는 320px이 아니라 418px

design-prompts는 "높이 320px", 아트보드는 418px이라 적었다. **둘 다 맞다** — 탭바
(64 + 하단 34 + 경계선 1 = 99px)가 시트 위에 떠서 아래를 덮으므로 보이는 높이가 319px이 된다.
"320px"은 탭바 하나선을 경계로 세는 어림값이다.

z-index는 **지도 기본 / 상단바 3 / 시트 4 / 탭바 5**.

시트 내용은 정확히 317px(핸들 9 + 10 + H1 30 + 10 + Meta 18 + 20 + 행 186 + 12 + 링크 22)이라
시트 안쪽 417px에 남는다. **시트를 스크롤 컨테이너로 만들지 않는다** — `overflow`는 `visible`이고
`scrollHeight === clientHeight`다.

## 12. 국가 위험도는 파생값 — VN은 HIGH가 아니라 CRITICAL

아트보드의 `HIGH`(#FF8A00)는 목 데이터보다 먼저 그려진 값이라 버린다.

국가 위험도는 **그 국가 법률의 최대 위험도**다 — §5의 S4 우선순위 타일과 같은 규칙이고,
`derive.ts`의 `maxRisk()` 하나를 둘이 같이 쓴다. VN은 `DECREE 110/2026`이 critical이므로
**CRITICAL(#FF3B30)**이다.

시트 H1 옆 배지와 지도 위 VN 마커 라벨이 같이 이 값을 본다 — 마커 문구가 `VN · CRITICAL`이 되는
이유다. 나머지 국가는 `company.json`의 `active: false`를 읽어 `ID · 곧 지원` / `TH · 곧 지원`이고,
KR만 출발지라 데이터에 없어 `KR · 출발` 상수다.

## 13. 시트 3행의 선정 규칙

아트보드의 3건(37 · 110 · 46)도 데이터 이전 값이라 버린다. `DECREE 46/2026`은 보류라 액션이 없어
"할 일"이 하나도 없는데 시트에 올라와 있다.

**규칙: 미완 액션이 있는 법률을 마감 임박순으로 정렬해 상위 3건.**

| 아트보드 | 데이터 파생 |
|---|---|
| DECREE 37/2026 · D-45 | **CIRCULAR 29/2023 · 기한 경과** |
| DECREE 110/2026 · D-14 | **DECREE 110/2026 · D-14** |
| DECREE 46/2026 · 보류 | **DECREE 37/2026 · D-45** |

액션이 없는 보류(46)와 휴면(15/2018)은 여기서 빠지고, 아래 링크 "법률 5건 모두 보기"가 전부를 받는다.
액션을 전부 체크해 0건이 되면 행 대신 Meta 한 줄 **"대응이 필요한 법률이 없습니다"**만 남는다.

행 수·건수·링크 문구는 전부 파생값이다. 문자열로 박지 않는다 — 아트보드의 `미완 액션 10`도
실제로는 **9**(액션 총 9건)다.

## 14. vaul을 설치하지 않는다

드래그로 펼친 뒤의 상태가 어느 문서에도 없고, 시트 내용이 418px에 정확히 맞아 확장할 것이 없다.
36×3 `--text-3` 핸들은 **시각 요소로만** 둔다 — 이 화면의 유일한 중앙 정렬이다(탭바와 함께
§4 좌측 정렬 규칙의 명시된 예외 둘).

검색과 "필터"도 아트보드가 `span`이라 비기능으로 둔다. 지원 국가가 VN 하나뿐이어서 검색이 할 일이
없다. `cursor:pointer`를 주지 않는다 — 아트보드의 "필터"에는 `cursor:pointer`가 붙어 있지만,
누를 수 없는 것에 누를 수 있다고 말하지 않는다.

검색 행의 하나선은 좌우 20px 안쪽으로 물러난다(바깥 `padding:0 20px`, 안쪽에 `border-bottom`).
아트보드 S5와 S2가 구조까지 같으므로 5단계의 S2 구현을 그대로 따랐다.

## 그 밖에 — `DotGeo`에 `onProject`를 되살렸다

원본 `neo-dots.js`는 `'neo-ready'` 이벤트로 projection을 밖에 넘겼고, 8단계 포팅에서 그 통로가
빠졌다. 마커를 점 위에 얹으려면 같은 투영이 필요하므로 선택 prop으로 되돌렸다.

콜백은 **ref로 받고 `useEffect` deps에 넣지 않는다.** 넣으면 인라인 함수를 넘긴 호출부에서
렌더마다 지도를 새로 만들고, 마커 좌표 `setState`까지 얽혀 순환한다.

# 10단계 판정 — 상태 화면

계획서 §8의 표는 "로딩 | 모든 목록", "에러 | 데이터 실패"라고 적었다. 이 앱의 데이터 경로를
보면 둘 다 존재하지 않는 상태다. 표를 그대로 옮기면 없는 지연을 만들어야 한다.

## 15. 목록 스켈레톤을 만들지 않는다

`data/*.json`은 `lib/data.ts`가 정적으로 임포트해 번들 안에 들어 있다. fetch가 없고 await가
없다. 목록이 "로딩 중"인 순간이 존재하지 않는다.

스켈레톤을 보여주려면 인위적 지연을 넣어야 하는데, 그건 사용자에게 없는 기다림을 만들어
보이는 것이다. **계획서 §8의 "로딩 | 모든 목록"을 폐기한다.**

앱에서 실제로 비동기인 것은 `/geo/land-110m.json` 하나뿐이다(`lib/geo.ts`).
그래서 스켈레톤도 `DotGeo` 자리에만 있다.

## 16. 데이터 에러 화면도 목록에 붙이지 않는다

같은 이유다. 목록이 실패할 경로가 없다. 에러는 두 곳에만 만든다.

| 자리 | 받는 것 | 문구 |
|---|---|---|
| `app/error.tsx` | 렌더 중 던져진 예외 | Body "규제 데이터를 불러오지 못했습니다" + "다시 시도" → `reset()` |
| `DotGeo` | land 로드 실패 | Meta "지도를 불러오지 못했습니다" + "다시 시도" → 재요청 |

`lib/geo.ts`가 실패 시 `landPromise`를 null로 비우므로 재시도가 실제로 새 요청을 낸다.
차단 → 에러 → 차단 해제 → "다시 시도"에서 `200 OK` 한 건이 나가고 지도가 그려지는 것을 확인했다.

## 17. `app/not-found.tsx` — 계획서에 없지만 열려 있던 구멍

`app/laws/[id]/page.tsx`가 `notFound()`를 부르는데 받는 화면이 없었다. Next 기본 화면은 흰
배경이라 단일 다크 테마가 그 순간 깨졌다. 계획서 §8에 없지만 에러 계열의 일부로 여기서 닫는다.

H1 "없는 법률입니다." + Meta 한 줄 + `--accent` 밑줄 "법률 목록으로". HTTP 상태는 404다.
**탭바를 두지 않는다** — 돌아가는 길 하나만 있는 모달성 화면이다. `app/error.tsx`도 같다.

## 18. S4 빈 상태는 도달하기 어렵다

`usePriorities`에 제거 기능이 없다(디자인에 없는 한 방향 동작). 기본값이 3건이라 0으로
내려갈 길은 `neo.priorities`에 빈 배열이 저장된 경우뿐이다. 그래도 만든다 — 타일 격자만
남고 아무 말이 없으면 무엇을 해야 하는지 알 수 없다.

`+ 영역 추가` 타일은 그대로 두고 그 아래에 Meta 한 줄만 얹는다.

## 19. 오프라인 바는 `Screen`이 렌더한다

여섯 화면이 전부 `Screen`을 쓰므로 한 곳만 고치면 된다. `Screen`에 `'use client'`가 붙는다 —
페이지들은 이미 전부 클라이언트다.

`getServerSnapshot`은 언제나 `true`(온라인)를 돌려준다. 서버는 `navigator`를 모르므로 서버에서
오프라인이라고 그려 두면 하이드레이션 불일치가 난다. 오프라인으로 시작한 경우에도 하이드레이션
직후 스냅샷 검사에서 바가 뜬다 — 첫 페인트에 한 프레임 늦는 대신 경고를 만들지 않는다.
확인: 여섯 라우트의 SSR HTML에 `role="status"`가 0건이고 콘솔 경고도 0건이다.

바가 켜지면 스크롤 영역 `top`을 `44px` → `calc(44px + var(--badge-h))`로 민다. 값을 두 번
적지 않으려고 `44 + 22`를 쓰지 않았다. 겹쳐서 상단바를 가리지 않는다.

**알려진 부작용**: S5 지도 박스는 아래 끝이 시트 상단(426px)과 정확히 맞닿아 있어서, 22px
밀리면 아래 22px이 시트 뒤로 들어간다. 그 띠에 있는 것은 육지 점의 1.27%(자바 남단)뿐이고
마커 4개(가장 낮은 ID가 y 312)와 항로는 전부 위에 있다. 오프라인 바 자체가 가리는 것은
아무것도 없다. S5만 예외 처리하는 것보다 이쪽이 낫다고 봤다 — "한 곳만 고친다"를 깨지 않는다.

서비스워커와 실제 캐시는 11단계다. 여기서는 연결 여부만 본다.

## 20. 스켈레톤은 `DotGeo` 안에서 처리한다

호출부(S1·S5) 두 곳이 같은 `loading | ready | error` 분기를 반복할 이유가 없다.
캔버스 위에 겹치고, 상태는 컴포넌트가 혼자 안다.

- **250ms 게이트.** `lib/geo.ts`가 모듈 레벨 Promise로 캐싱하므로 두 번째 마운트부터 즉시
  끝난다. 게이트가 없으면 그때마다 블록이 한 프레임 깜빡인다. 확인: 캐시된 뒤 /laws ↔ /map을
  왕복해도 `.neo-pulse`가 한 번도 나타나지 않았다(MutationObserver).
- **shimmer 금지.** `@keyframes neo-pulse`는 `opacity`만 건드린다(1 ↔ .45, 1.6s ease-in-out).
  실측에서 `background-image: none` · `transform: none` · `filter: none`을 확인했다 —
  좌→우 광택을 만들 기제가 아예 없다.
- **`prefers-reduced-motion: reduce`에서 `animation: none`.** 블록은 남긴다 — 자리를 비우면
  무엇을 기다리는지 알 수 없다.
- `aria-hidden="true"`를 host div에서 캔버스로 내렸다. 에러 문구와 "다시 시도"가 읽혀야 한다.

## 그 밖에

`EmptyState`에 `size`(`'body' | 'meta'`) 하나를 뒀다. 계획서는 S2 목록 자리를 Body로,
판정 4는 S4를 Meta로 적었고 둘 다 맞다 — 목록을 대신하는 문구와 타일에 붙는 곁말은 위계가
다르다. 빈 상태 문구 색은 전부 `--text-3`으로 맞췄다(9단계 S5의 빈 줄과 같다).

오프라인 바 문구에 `tnum`을 넣었다. 시각 문자열이고, 앱의 다른 시각 표시가 전부 그렇다.

`button`의 UA 기본 `text-align: center`를 `EmptyState` 액션에서 `left`로 덮었다. 줄어든
폭이라 눈에 보이는 차이는 없지만 §4 좌측 정렬 전수 검사를 통과해야 한다.

# 11단계 판정 — PWA

계획서 §9는 Serwist + `data/*.json` stale-while-revalidate + Lighthouse PWA 통과로 적혀 있다.
세 가지 모두 이 앱에서는 성립하지 않는다.

## 21. `data/*.json`은 캐싱 대상이 아니다

lib/data.ts가 정적으로 임포트해 JS 청크 안에 들어 있고 독립된 URL이 없다.
없는 URL에 stale-while-revalidate를 걸 수 없다 — 10단계 판정 15와 같은 이유다.

런타임 캐싱 대상은 **실제로 URL을 갖는 것뿐**이다.

| 대상 | 전략 |
|---|---|
| 문서(내비게이션) · RSC 페이로드 | network-first → 캐시 폴백 |
| `/_next/static/*` · `/fonts/*` · `/geo/*` · `/icons/*` · 매니페스트 · 파비콘 | cache-first |
| 그 밖 | 손대지 않고 통과 |

빌드 산출물 프리캐시 매니페스트도 만들지 않는다. 해시 파일명을 알려면 빌드 훅이 필요한데
`/_next/static/*`은 해시가 붙어 불변이므로 cache-first 런타임 캐싱으로 충분하다.
install에서는 URL이 고정된 13개만 받는다.

## 22. 프리캐시할 라우트는 앱이 서비스워커에 알려준다

public/sw.js는 정적 파일이라 data/laws.json을 임포트할 수 없다. 법률 5건의 id를 거기 박으면
파생값 원칙이 깨진다. `components/ServiceWorker.tsx`가 `lib/data`의 laws에서 URL을 만들어
postMessage로 넘기고 SW가 받아 캐시한다. 법률이 늘면 목록도 같이 는다.

**개수는 10개다** (판정 문서의 "11개"는 셈이 틀렸다). 6화면 중 S3는 URL이 아니므로
정적 라우트는 5개(`/` `/laws` `/company` `/map` `/notifications`)이고 법률 상세 5건을 더해 10이다.
코드가 `laws`에서 계산하므로 숫자를 박은 곳은 없다.

## 23. 문서와 RSC는 다른 캐시에 담는다

클라이언트 내비게이션은 문서가 아니라 RSC 페이로드(`?_rsc=<해시>`)를 받는다.
해시가 빌드마다 바뀌므로 URL 완전 일치로는 찾을 수 없어 **키를 쿼리 없는 경로로 정규화**한다.

한 캐시에 담고 `ignoreSearch`로 찾는 것은 안 된다 — `/laws` 문서와 `/laws?_rsc=…` 페이로드가
서로를 물어 오고, 라우터가 HTML을 flight 페이로드로 파싱하려 든다. 그래서 캐시를 둘로 나눈다
(`neo-v1` / `neo-v1-rsc`).

**RSC 페이로드도 프리캐시한다.** 처음에는 문서만 담았는데, 오프라인에서 탭을 누르면 아무 일도
일어나지 않았다 — RSC 요청이 실패하고 라우터가 하드 내비게이션으로 떨어지지도 않고 그냥 멈춘다.
해시를 몰라도 받을 수 있다: `RSC: 1` 헤더로 요청하면 Next 16이 `<경로>?_rsc`로 307을 주고,
그 URL이 같은 페이로드를 돌려준다(`text/x-component`). 그래서 라우트마다 문서와 RSC를 함께 담는다.
첫 방문 한 번으로 문서 10건 + RSC 10건이 결정적으로 채워진다 — Next의 링크 프리페치에 기대지 않는다.

## 24. 매니페스트는 `app/manifest.ts`로 쓴다

public/manifest.json이 아니다. 타입 검사가 붙고 layout.tsx의 metadata와 한곳에서 관리된다.
산출 URL이 `/manifest.webmanifest`(`application/manifest+json`)이므로 프리캐시 목록도 그 URL을 쓴다.

## 25. 아이콘은 앱의 서명인 施다

`var(--bg)` 바탕에 `var(--accent)` 글리프. 아이콘은 화면 콘텐츠가 아니므로 좌측 정렬 규칙을
적용하지 않고 글리프를 중앙에 둔다.

**기기 폰트에 기대지 않는다.** `public/fonts/neo-mark-65BD.woff2`를 그대로 래스터화한다 —
施가 플랫폼마다 다른 골격으로 찍히는 것을 막으려고 그 폰트를 자체 호스팅했는데, 아이콘이
시스템 명조로 찍히면 같은 문제가 홈 화면에서 되살아난다.

`scripts/make-icons.mjs`가 `@resvg/resvg-js`로 만든다. resvg의 fontdb는 woff2를 읽지 못해
("malformed font") **`wawoff2`로 압축만 풀어** 임시 ttf로 넘긴다 — 아웃라인은 손대지 않는다.
글리프 잉크 경계를 `getBBox()`로 재고 그 중심을 캔버스 중심에 맞춘다. 施는 좌우 여백이
대칭이 아니라 advance width로 놓으면 눈으로 봤을 때 가운데가 아니다.

색은 `app/globals.css`의 토큰에서 읽는다. 아이콘 스크립트에 색을 다시 적지 않는다.

크기는 192·512(any) · 512(maskable) · 180(apple-touch)이고 **maskable은 any × 0.8**이다 —
maskable 안전영역이 캔버스의 중앙 80%라서, 안전영역 대비 글리프 비율을 any의 캔버스 대비
비율과 같게 맞춘 값이다. 두 아이콘이 각자의 틀 안에서 같은 무게로 보인다.

## 26. Lighthouse PWA 통과는 검증 기준이 될 수 없다

Lighthouse 12에서 PWA 카테고리가 제거됐다. 설치 가능 조건을 직접 확인하는 것으로 대체한다.
가장 강한 신호는 **`beforeinstallprompt`가 실제로 발화하는 것**이다 — 크롬은 매니페스트
필수 항목(name/short_name·start_url·display·192/512 아이콘·maskable)과 fetch 핸들러를 가진
서비스워커가 모두 통과할 때만 이 이벤트를 쏜다. 2회차 방문에 배너가 뜬 것이 그 증거다.

## 27. 오프라인 바 문구는 REFERENCE_DATE 기준 그대로 둔다

실제 캐시 시각으로 바꾸면 기준 날짜 단일 출처 원칙이 깨진다. 실 서비스에서 `lastSync`가
생기면 그때 바꾼다. 지금 바는 연결 여부만 본다 — 캐시가 실제로 언제 채워졌는지는 모른다.

## 28. 설치 배너는 아트보드에 없다 — 기존 행 문법으로 짠다

색면으로 만들지 않는다. S6의 시안 색면("시행일 알림 켜기")과 위계가 부딪친다 —
저 블록은 놓치면 손해를 보는 것이고 이건 있으면 편한 것이다.

탭바(z-index 5) 바로 아래 `bottom: 98`에 z-index 4로 앉는다. 탭바의 상단 하나선이 위에
그려져 배너와 탭을 가르므로 보이는 높이는 63px이다. 배너가 뜨면 S1의 `scrollPadBottom`을
130 → 194로 같이 민다 — 마지막 행이 배너 뒤로 들어가면 안 된다.

2회차 방문부터 뜨고(`neo.visits`, 모듈 로드 시 한 번 증가 — 클라이언트 내비게이션으로는
늘지 않는다), "나중에"를 누르면 다시 뜨지 않는다(`neo.install.dismissed`).
`beforeinstallprompt`가 없는 브라우저에서는 아예 뜨지 않는다 — iOS Safari가 그렇고,
거기서는 공유 시트의 "홈 화면에 추가"뿐이라 우리가 대신 눌러 줄 방법이 없다.
없는 버튼을 안내 문구로 흉내내지 않는다.

## 그 밖에 — 검증에서 잡힌 것 둘

**`.gitignore`가 서비스워커를 삼키고 있었다.** `public/sw*.js`와 `public/workbox-*.js`를
무시하는 줄이 있었다. Serwist·next-pwa가 **생성하는** 산출물을 걸러내려던 규칙인데,
4단계 판정에서 서비스워커를 직접 쓰기로 했으므로 `public/sw.js`는 생성물이 아니라 소스다.
그대로 커밋하면 서비스워커가 조용히 빠진 채 배포됐을 것이다. 두 줄을 지웠다.

**버전을 올린 직후 라우트 프리캐시가 유실됐다.** 등록 직후 `controller`에게 postMessage하고
`controllerchange`를 `{ once: true }`로 듣던 구조라, 재배포 직후 로드에서는 물러나는 옛 워커에게
메시지가 가고 새 셸에는 고정 URL 13개만 남았다(라우트 10개가 비었다). `once`를 떼고 제어권이
넘어올 때마다 다시 보내도록 고쳤다 — 같은 URL을 다시 담는 것은 무해하다.
검증 8이 잡아낸 것이고, 고친 뒤 재확인해 v2 셸에 23건이 그대로 들어갔다.

# 12단계 판정 — 최종 대조

앞선 세션이 한도로 끊기면서 수정 1·4·5(v0.2.0~v0.4.0)가 트리에 남지 않았다.
커밋도 미커밋 변경도 다른 사본도 없어 이 세션에서 다시 구현하고 12단계를 진행했다.
아래는 재구현에서 갈린 판단과 대조 결과다.

## 29. 아이콘은 이제 施가 아니라 법봉이다 — §25 번복

§25는 "아이콘은 앱의 서명인 施다"였다. 업로드된 `mobile.png`(법봉 픽셀아트)로 교체하기로
승인받아 뒤집는다. 매니페스트 3종과 apple-touch-icon 모두 같은 원본에서 나온다.

원본을 그대로 쓰지 않은 이유가 셋이다.

1. **992×1069라 정사각형이 아니다.** iOS는 apple-touch-icon을 레터박스하지 않고 늘린다.
2. **흰 배경이다.** 앱은 `#171717`인데 아이콘만 흰 판이면 홈 화면에서 끊긴다.
3. **173KB다.** 아이콘 하나에 그만큼 쓸 이유가 없다.

그래서 잉크 경계(745×629)를 재서 정사각 캔버스에 다시 앉히고 배경 `--bg` · 법봉 `--accent`로
갈아입혔다. §25의 색 규칙은 그대로 살아 있다 — 바뀐 것은 글리프뿐이다.

**계획의 "180 산출물 제거"는 취소했다.** apple-touch-icon도 같은 생성기를 타는 정사각
산출물이 되었으므로 지울 이유가 없다. 지우면 비정사각 173KB 원본을 애플에 넘기게 된다.

`scripts/make-icons.mjs`는 글리프 래스터화에서 PNG 리샘플로 다시 썼다. 외부 이미지
라이브러리를 쓰지 않는다 — 원본이 8비트 RGBA 비인터레이스라 `zlib` 하나로 디코드되고
인코드도 IHDR·IDAT·IEND 셋뿐이다. 축소는 넓이 평균이다. 1px 픽셀아트 선을 최근접으로
줄이면 선이 사라진다. 이 재작성으로 `@resvg/resvg-js`와 `wawoff2`가 미사용이 되어 뺐다.

원본 아트는 `design/mobile.png`에 둔다. `public`은 실제로 배포되는 것만 담는다.

**업로드된 `favicon.ico`는 그대로 쓴다 — 승인 사항.** 다만 기록해 둔다: 16×16 픽셀을
디코드해 보면 가장 어두운 픽셀이 188 회색이고 256px 중 144px이 순백이다. 992px 선화를
16px로 줄이면서 검은 선이 날아간 상태라 밝은 배경 탭에서는 사실상 보이지 않는다.
다시 만들자고 제안했으나 업로드 파일을 쓰기로 정해졌다.

## 30. 확대 금지는 접근성과 맞바꾼 값이다 (WCAG 1.4.4)

`maximumScale: 1` · `userScalable: false`는 WCAG 1.4.4(200% 확대)에 어긋난다.
"앱처럼 다뤄지게 한다"는 요구를 우선했고, 대신 본문 최소 크기를 15px로 유지해 확대 없이
읽히게 뒀다. 되돌릴 때는 이 두 줄만 빼면 된다.

iOS Safari 10+는 이 둘을 무시한다. 실기기에서 핀치가 살아 있을 수 있는데,
**`gesturestart` 차단은 넣지 않았다** — 실기기로 확인하지 못했고, 확인 없이 넣으면
살아 있지도 않은 제스처를 막는 코드가 남는다.

## 31. safe-area는 아트보드의 44/34가 아니라 env()다

`--safe-top` · `--safe-bottom` 두 토큰이 `env()`를 읽는 유일한 곳이다.
하드코딩을 걷어낸 곳 넷: `Screen`(상단 44 → `--safe-top`, 오프라인 바 오프셋 포함),
`OfflineBar`(top 44), `TabBar`(paddingBottom 34), `InstallBanner`(bottom 98 →
`calc(64px + --safe-bottom)`).

**브라우저 탭에서는 두 값이 0이다.** 아트보드의 44px 상태바 띠가 사라지는데 이게 맞다 —
없는 상태바를 흉내 내면 빈 띠만 남는다. `screens.png`와의 이 차이는 의도된 것이다.

`app/*/page.tsx`의 `height: 44` 넷은 검색창·CTA 버튼 높이지 안전영역이 아니다. 두었다.

S5 지도 박스는 `Screen` 스크롤 영역 기준 `absolute`라 `--safe-top`만큼 함께 밀린다.
47/34를 주입해 상단 띠·탭바 여백·지도가 같이 자라는 것을 확인했다.

## 32. 오프라인은 문서만 담기고 청크가 빠진다 — 범위 밖으로 둔다

**12단계 회귀 기준 "오프라인에서 10개 라우트가 열린다"를 온전히 만족하지 못한다.**
고치지 않기로 결정됐다. 상태를 그대로 적는다.

프로덕션 빌드를 띄우고 서버를 실제로 내려 검증했다.

- 프리캐시 자체는 정상이다. `neo-v2`와 `neo-v2-rsc`에 라우트 10개가 정확히 담긴다.
- 그런데 **콜드 첫 설치 직후 캐시된 JS 청크가 0개**다. 첫 방문의 청크 요청은
  서비스워커가 제어권을 잡기 전에 끝나 가로채지 못한다.
- 결과: 오프라인에서 페이지가 프리렌더 HTML로 열리기는 하지만 하이드레이션이 안 된다.
  스크립트 9개 전부 실패하고, 체크박스를 눌러도 `aria-checked`가 바뀌지 않으며
  localStorage에도 쓰이지 않는다. S5 마커도 붙지 않는다.
- 청크가 **일부만** 캐시된 중간 상태는 더 나쁘다. `ChunkLoadError`가 에러 바운더리까지
  올라가 화면이 "규제 데이터를 불러오지 못했습니다"로 통째로 대체된다.
  `/map`과 `/laws/[id]`에서 재현했다.
- 대조 실험으로 확정했다. 온라인에서 10라우트를 모두 방문해 청크 15개를 받아둔 뒤
  서버를 내리면 같은 라우트가 전부 정상 렌더된다.

원인은 §22가 선 이 전제다 — "`/_next/static/*`은 해시가 붙어 불변이므로 cache-first
런타임 캐싱으로 충분하다." cache-first는 **요청된 적 있는** 것만 담는다. 방문한 적 없는
라우트의 청크는 캐시에 영원히 들어오지 않는다. 전제가 틀렸다.

고칠 때의 선택지 셋. 권하는 것은 (b)다.

- (a) 빌드 후 `.next` 산출물을 훑어 프리캐시 매니페스트를 생성한다. §22가 피하려던 빌드 훅이 필요하다.
- (b) `ServiceWorker.tsx`가 라우트 문서를 프리캐시할 때 그 HTML에서 `<script src>`를
  파싱해 청크 URL까지 함께 넘긴다. 빌드 훅 없이 §22의 "앱이 알려준다" 구조와
  파생값 원칙을 그대로 유지한다.
- (c) 오프라인 범위를 "읽기 전용"으로 낮추고 명세를 고친다.

## 35. 원인은 `bottom: env()`가 아니었다 — 후보 5개 중 3개가 실제 원인

인수인계가 제시한 첫 후보(`bottom: env(safe-area-inset-bottom)`)는 **원인이 아니다.**
`git log -p components/TabBar.tsx`로 확인했다 — 탭바는 처음부터 `bottom: 0` +
`padding-bottom: var(--safe-bottom)`이었고 한 번도 다른 적이 없다.
`viewport-fit=cover`도 meta에 정상 출력되고 있었다. 실제 원인은 아래 셋이다.

### 원인 1 — 프레임 `maxWidth: 390`이 기기 폭이 아니다 (증상 3)

390은 아트보드 폭이다. 실제 아이폰은 393(16)·402(16 Pro)·430(16 Plus)·440(16 Pro Max)다.
`Screen`이 390으로 잘라 가운데 두므로 402pt 기기에서 **프레임이 x=6에서 시작**한다.
탭바·CTA 바·시트가 전부 프레임 안쪽이라 같이 6pt 밀리고, 좌우에 배경과 같은 색
검은 띠가 남는다. 인디케이터는 자기 탭 셀과는 정확히 맞아 있었다 —
어긋난 것은 **셀이 아니라 화면 좌측 끝**이었고, 사용자가 본 "약 5pt"가 이 6pt다.

측정: 402 뷰포트에서 `frame.x = 6`, `nav.x = 6`, `indicator.x = 6`.

**조치**: `--frame-max: 440px`. 현재 가장 넓은 아이폰까지 꽉 채우고,
그보다 넓은 데스크톱에서만 프레임으로 잘린다. 390 고정을 유지하면 402·430·440pt
기기에서 영구히 검은 띠가 남는다. 콘텐츠는 좌측 정렬이라 폭이 늘어도 어법이 유지되고,
우측으로 흘리는 지구본·지도(`margin-right: -36`)도 그대로 흘러 나간다.
조치 후 측정: `frame.x = 0, w = 402`, `nav.x = 0, w = 402`, `nav.bottom = 874`(화면 최하단),
인디케이터 x/폭이 4개 탭 셀(0·101·201·302, 폭 101)과 일치.

### 원인 2 — `apple-mobile-web-app-capable`이 출력되지 않는다 (증상 1)

`layout.tsx`의 `appleWebApp.capable: true`는 **Next 16에서 표준명
`mobile-web-app-capable` 하나만** 내보낸다. iOS Safari는 그 이름을 모른다.
애플 접두 이름이 없으면 iOS는 같이 준 `apple-mobile-web-app-status-bar-style:
black-translucent`를 통째로 무시하고, 웹뷰가 화면 전체를 덮지 않아
`env(safe-area-inset-*)`이 0으로 접힌다. 그 결과가 "탭바가 홈 인디케이터보다
훨씬 위에 떠 있고 그 아래로 배경색과 같은 검은 띠가 남는" 증상이다.

확인: 배포 전 HTML에 `apple-mobile-web-app-capable`이 **없었다**(`curl | grep`).

**조치**: `metadata.other`로 애플 이름을 직접 더한다. 표준명은 Next가 이미 내므로
둘 다 나간다. 조치 후 HTML에 두 meta가 모두 출력됨을 확인했다.

### 원인 3 — 하단 여백이 화면마다 다른 숫자였다 (증상 2)

`scrollPadBottom`이 화면마다 `130 / 180 / 180 / 140 / 40 / 0`으로 박혀 있었고
**어느 것도 안전영역을 항으로 갖지 않았다.** 숫자가 6개면 기기마다 6가지로 어긋난다.

**조치**: 토큰 하나에서 전부 계산한다.

```
--tabbar-cell: 64px            탭 셀 (TabBar가 이 값을 쓴다)
--tabbar-h:    cell + 1px      상단 하나선 포함한 바 실제 높이
--ctabar-cell: 56px            S3 CTA 셀
--ctabar-h:    cell + 1px
--pad-tabbar:  --tabbar-h + --safe-bottom + 24px    S1/S2/S4
--pad-ctabar:  --ctabar-h + --safe-bottom + 24px    S3
--pad-plain:   --safe-bottom + 24px                 S6·에러·404 (하단 바 없음)
```

`Screen`의 `scrollPadBottom`을 `number`에서 CSS 길이 문자열로 바꿨다. 숫자를 받으면
`calc()`를 넘길 수 없어 안전영역을 항으로 넣을 방법이 없다.
`InstallBanner`의 `calc(64px + ...)`도 `--tabbar-h`로 바꿨다 — 기존 값은 하나선 1px이 빠져 있었다.

## 36. S3 CTA 바에는 안전영역이 아예 없었다

`AddActionsBar`가 `bottom: 0; height: 56`뿐이라 CTA 버튼이 홈 인디케이터 아래로 들어간다.
탭바와 같은 규칙으로 고쳤다 — 바깥이 `padding-bottom: var(--safe-bottom)`,
안쪽 div가 `height: var(--ctabar-cell)`. 높이를 고정하지 않는 이유는 Tailwind 리셋의
`box-sizing: border-box` 때문이다. `height: 56px` + `padding-bottom: 34px`를 같이 주면
셀이 22px로 찌그러진다.

측정: 안전영역 34에서 버튼 하단이 화면 바닥에서 40px 위(34 + 셀 여백 6),
안전영역 0에서 6px 위. 두 경우 모두 본문과의 여백은 정확히 24px.

## 37. S5 시트 높이 418은 안전영역 0 기준값이었다

시트가 `height: 418` 고정이라 탭바가 안전영역만큼 두꺼워지면 그만큼 잠식된다.
측정: 마지막 행("법률 N건 모두 보기")과 탭바 사이가 안전영역 0에서 37px,
34에서 **3px**. 같은 화면이 기기에 따라 34px씩 달라지고 있었다.

**조치**: `height: calc(418px + var(--safe-bottom))`. 418은 §11에서 확정한
안전영역 0 기준 실측값이므로 그대로 두고 항만 더한다. 시트 위에 탭바가 겹쳐 앉는
구조(z-index 4 / 5)는 유지한다. 조치 후 두 경우 모두 37px.

## 39. 실기기 확인 결과 — `100dvh`가 iOS Safari에서 굳는다

사용자 실기기 스크린샷으로 §38이 반증됐다. 재현 환경이 standalone이 아니라
**Safari 브라우저**였고, 스크린샷 두 장이 원인을 그대로 보여준다.

| 스크린샷 | Safari 하단 툴바 | 탭바 위치 |
|---|---|---|
| 1 | 펼침 (URL 바 보임) | 툴바 바로 위 — 정상 |
| 2 | 접힘 (작은 알약만) | 툴바가 비운 만큼 **위에 떠 있고 아래는 배경색 띠** |
| 3 (데스크톱) | 없음 | 정상 |

**원인**: `Screen`의 프레임이 `height: 100dvh`였다. `dvh`는 레이아웃 값이라
브라우저가 리레이아웃을 걸어야 갱신된다. 그런데 이 앱은 `html·body`가
`overflow: hidden`이라 **문서 자체가 스크롤되지 않는다.** 스크롤은 전부 프레임 안쪽
컨테이너가 받는다. 그래서 Safari가 툴바를 접어도 문서 쪽에는 아무 일도 일어나지 않고,
프레임은 접히기 전 높이(작은 뷰포트)에 굳은 채 남는다. 그 차이가 탭바 아래 띠다.

`svh`·`lvh`로 바꾸는 것은 답이 아니다. `svh`는 접혔을 때 같은 띠가 남고,
`lvh`는 펼쳤을 때 탭바가 툴바 뒤로 들어간다. 둘 다 한쪽 상태에서만 맞다.

**조치**: 뷰포트 단위를 쓰지 않는다. 바깥 래퍼를 `position: fixed; inset: 0`으로
두고 프레임을 그 `height: 100%`로 잡는다. fixed 요소는 브라우저가 툴바 상태에 맞춰
직접 옮겨 주므로 CSS 길이가 굳는 문제가 없다. 사용자 요청("Safari 위젯을 고려하지 말고
최하단으로")은 두 해석 모두에서 충족된다 — Safari가 fixed 요소를 툴바 위로 밀어
주면 툴바 바로 위, 밀지 않으면 화면 최하단이다. **어느 쪽이든 띠는 생기지 않는다.**
standalone·안드로이드·데스크톱에는 툴바가 없어 동작이 바뀌지 않는다.

아이폰 SE 375 → 프레임 x 0 · w 375 풀블리드, 탭바 bottom 667.

## 42. 선택 행은 자신과 바로 아래 행의 헤어라인을 둘 다 지운다

# 2차 작업 — B2 (데이터 스키마 재구조화)

## 51. 조합 파일은 `{ laws, actions }` 한 덩어리다

지시서 §B-2는 `data/laws/VN-food.json` 하나만 적었고 액션 파일은 말하지 않았다.

`data/laws.json`과 `data/actions.json`은 지웠다. 12개 파일이 정적 임포트로 묶인다 —

## 57. ⚠ B1의 실제 버그 — 프로필이 있는데 새로고침하면 /setup으로 튕겼다

`useSyncExternalStore`는 hydration 렌더에서 `getServerSnapshot()`(= `null`)을 쓴다.

스토어 스냅샷이 이미 맞아 있었다. "새로고침에서 크래시 없음"만 보고
"새로고침에서 프로필이 유지되는가"를 보지 않았다.

**조치**: 판정을 `readProfile()`로 바꿨다. 모듈 로드 때 localStorage에서 읽은 값이라
클라이언트에서는 언제나 정확하다. `useProfile()`은 저장 직후 이펙트를 다시 돌리기 위한
구독으로만 남긴다. 확인: 프로필을 넣고 `/`를 새로고침 → `/` 유지, H1 `대응 필요 3건`.

## 59. 파생 함수는 `Dataset`을 인자로 받는다

"이번 주"에 서 있었다. 앞뒤 7일 안에 기준 날짜(기한 ?? 시행일)가 드는 법률로
바꿨고, **0건이면 섹션 자체를 그리지 않는다.** 아무 일도 없는 주에 "이번 주"라는
라벨만 남기지 않는다. 지금 데이터에서는 THIS WEEK가 뜨지 않는다 —
5건의 날짜가 전부 7일 밖이다. B5·B6에서 최근 법령이 들어오면 다시 뜬다.

## 75. 날짜 파생값은 클라이언트에서만 계산한다

`TODAY`를 모듈 상수로 두면 정적 배포에서 **빌드한 날이 영원히 오늘**이 되고,
서버가 찍은 값과 클라이언트 값이 달라 hydration이 깨진다.

- `Dataset.today`가 날짜의 유일한 출처다. `Dataset`은 프로필이 있어야 만들어지고
  프로필은 hydration 이후에야 읽히므로 자연히 클라이언트 전용이다.
- `/laws/[id]`는 서버 컴포넌트라 헤더 배지만 `HeaderBadge.tsx`로 떼어냈다.
  `useSyncExternalStore`로 읽는다 — `useEffect` + `setState`는 렌더를 한 번 더 돌려
  스켈레톤이 한 프레임 깜빡인다.
- `new Date()` 호출은 `lib/dday.ts` 한 곳뿐이다. 나머지는 프로필 `updatedAt`(실제
  발생 시각)과 React key용 `Date.now()`뿐이고 D-Day와 무관하다.

`referenceDate`는 `"today"` | ISO 둘을 받고 기본값이 `"today"`다.
고정 경로 검증: `2026-09-03T08:12+09:00`으로 고정하니 D-503 → D-506으로
정확히 3일 움직였다.

## 76. 상단바의 "마지막 동기화 시각"을 버렸다

`09.03 08:12`는 동기화하는 서버가 없으므로 지어낸 시각이었다. 실제로 말할 수 있는
것은 "우리가 이 출처들을 언제 열어 봤는가"뿐이다. 조합 안 법령의 가장 최근
`source.lastVerified`를 `2026.09.01 확인`으로 적는다.

오프라인 바도 같은 이유로 시각을 뺐다. 캐시가 언제 만들어졌는지 그 컴포넌트는
모르고, 아는 척하려면 날짜를 지어내야 한다. `오프라인 · 저장된 데이터로 표시 중`.

## 77. 알림을 법령에서 파생시킨다 (§B-5)

`data/notifications.json`을 지웠다. 고정 타임스탬프 6건이라 기준일이 오늘로 바뀌면

# 2차 작업 — 공용 법령 파일 (§82 해결, 사용자 확정)

## 85. `<국가>-shared.json` — 여러 품목에 걸치는 법령

```
data/laws/
  VN-shared.json      품목을 가리지 않는 법령 (상품 라벨 시행령 등)
  VN-food.json        식품 전용
  VN-cosmetics.json   화장품 전용
  …
```

**법령을 복사하지 않는다.** 법령 id가 전역에서 유일해야 `/laws/[id]` 정적 생성과
id 조회가 성립하는데, 복사하면 id 하나가 서로 다른 액션 집합 여럿을 가리킨다.
대신 **액션 쪽에 품목을 단다** — `Action.itemCategories?: ItemCategoryId[]`.

`lawSetOf(country, category)`가 조합 파일 + 공용 파일을 합치면서
법령은 `law.itemCategories`로, 액션은 `action.itemCategories`로 거른다.
공용 법령을 앞에 세운다 — 품목을 가리지 않는 규정이 대개 더 넓게 걸린다.

검증: `/laws/VN-2026-037` 하나가 프로필에 따라 다른 액션을 보여준다.

| 프로필 품목 | MUST DO — 3 |
|---|---|
| 식품·음료 | 라벨 시안 재작성 · 인쇄 포장재 소진 계획 · **식품 표시사항(원산지·영양성분)** |
| 화장품 | 라벨 시안 재작성 · 인쇄 포장재 소진 계획 · **화장품 전성분·사용기한** |

## 86. 빈 `hsPrefixes`는 '모른다'가 아니라 '구분이 없다'

상품 라벨 시행령은 HS 코드와 무관하게 모든 제품에 걸린다. `hsPrefixes: []`가
그 뜻이고, `productsMatching`은 빈 배열이면 전 제품을 돌려준다.
**공용 파일에서만 허용한다** — 조합 파일에서 비면 그건 조사를 덜 한 것이다.
`check-data.mjs`가 그 구분을 강제한다.

## 87. S3의 MUST DO 섹션이 클라이언트로 내려갔다

액션 수가 품목에 따라 달라지는데 **서버는 사용자의 품목을 모른다** —
프로필이 localStorage에 있기 때문이다. 그대로 두면 화장품 사용자의 라벨 시행령
화면에 "영양성분 베트남어 표기"가 섞인다. 섹션 라벨(`MUST DO — N`)까지
`MustDoList`가 그린다. 하단 여백은 여전히 서버가 전역 액션 유무로 잡는다 —
'바가 있을 수 있는가'만 알면 되고, 실제로 그릴지는 클라이언트가 정한다.

## 88. `check-data.mjs`가 보는 것 (추가분)

- 공용 파일: `itemCategories`가 비었거나 품목이 하나뿐이면 실패
  (하나뿐이면 공용이 아니라 그 조합 파일에 둔다)
- 공용 파일의 액션: `itemCategories`가 그 법령의 `itemCategories` 밖을 가리키면 실패
- 조합 파일의 액션에 `itemCategories`가 붙어 있으면 실패 — 이미 그 품목 전용이다
- 빈 `hsPrefixes`는 공용 파일에서만 허용

## 91. 유예 종료일이 우리 제품의 기한이 아닐 수 있다

`CIRCULAR 56/2025/TT-BKHCN`(LED)의 경과규정은 이렇게 생겼다.

```

2027-01-01  HS 9405.11.99 포함 전 품목 적용
```

`2027-01-01`을 `deadline`에 넣으면 **D-117**이 뜬다. 화면은 좋아지지만 거짓말이다.
우리 제품은 LED 전구 `8539.52`이고 그건 **2026-06-01부터 이미 대상**이다.
2027-01-01은 조명기구(9405)의 날짜다.

아직 안 했다"가 정확한 상태다. 유예 사실 자체는 버리지 않고 `transitionEndsAt`

**규칙**: 법령에 날짜가 적혀 있다고 다 `deadline`이 아니다. **그 날짜가 우리

"없는 날짜를 지어낸 것"이었고, 이건 "있는 날짜를 엉뚱한 제품에 붙이는 것"이다.
결과는 같다.

## 95. ⚠ 시드 법령 하나가 이미 폐지돼 있었다

`CIRCULAR 29/2023/TT-BYT`(영양성분 표시)는 **2026-07-10부로 효력을 잃었다.**
`THÔNG TƯ 30/2026/TT-BYT`(2026-07-09 공포)가 대체했다.
재검증을 하지 않았으면 **폐지된 통칙을 현행 의무로 계속 보여줬을 것이다.**

§93이 시드의 `publisher` 표기를 지적했고, §92가 시드의 법령 배치를 지적했는데,
이번 것은 한 단계 더 나쁘다 — **법령 자체가 살아 있지 않았다.**
번호·시행일·`changes`가 전부 맞아도 그것이 아직 유효한지는 별개의 질문이다.

**규칙**: 재검증은 "이 값이 맞는가"가 아니라 **"이 법령이 아직 살아 있는가"부터**
묻는다. 대체·폐지 여부를 먼저 확인하고 그다음 세부 값을 본다.
시드 데이터의 다른 조합에도 같은 위험이 있다.

**id는 새로 팠고(`VN-2023-029` → `VN-2026-030`) 액션 id는 그대로 뒀다.**
법령이 바뀌어도 할 일의 종류(시험성적서 확보 · 라벨 반영)는 같다.
`VN-a-08` · `VN-a-09`의 `lawId`만 새 법령으로 돌렸다 — `neo.actions.done`이
그 id를 담으므로 바꾸면 사용자의 완료 표시가 날아간다(§52 · §92 · 4차 §1-15).

## 96. `DECREE 37/2026` 경과 종료일 — 2028-01-23으로 확정

제98조 4항은 달력 날짜를 쓰지 않는다 —

"2년을 넘지 않는다"이므로 그날까지는 아직 2년 안이다. 베트남 민법(2015)

**법이 실제로 쓰는 문장을 앞에 두고 계산 결과를 뒤에 붙이는 형태**로 바꿨다.
달력 날짜만 적으면 그 날짜가 법령에 쓰여 있는 것처럼 읽힌다.

## 97. 관보는 DOCX를 같이 올린다 — PDF가 스캔이면 그쪽을 연다

§89가 확립한 "원문 PDF를 zlib로 푼다"가 이번에는 통하지 않았다.
`datafiles.chinhphu.vn`의 서명본 PDF 세 건(`37-1.signed.pdf` ·
`31-bct.pdf` · `11-bct.pdf`)이 **전부 스캔 이미지**라 텍스트 스트림이 0개였다.
`vasep.com.vn`이 올린 `30-2026TT-BYT.pdf`는 스트림은 나왔으나 서브셋 폰트라
글자가 깨졌다.

`congbao.chinhphu.vn`(관보)은 같은 문서를 **PDF와 DOCX 둘 다** 올린다.
DOCX는 zip이므로 로컬 헤더를 훑어 `word/document.xml`을 `inflateRawSync`로 풀면
성조 글자까지 온전한 텍스트가 나온다. `DECREE 37/2026`은 266,344자를 얻었다.

```js
// zip 로컬 헤더(PK\x03\x04)를 찾아 word/document.xml만 inflateRawSync
// 태그를 벗기고 <w:p>를 줄바꿈으로 바꾼다 — 외부 의존성 없이 zlib만 쓴다
```

**우선순위**: 관보 DOCX → 관보 PDF(zlib) → 부처 CDN PDF(zlib) → 2차 출처 교차확인.
부처 통칙은 관보에 실리지 않는 경우가 많다(`30/2026/TT-BYT` · `24/2019/TT-BYT`가
그랬다) — 그때는 `secondary`로 두고 독립 출처를 늘린다.

## 98. 범위를 모르면 넣지 않는다 — §89의 뒤집힌 적용

§89는 2차 출처가 통칙의 적용 범위를 **좁게** 말한 것을 원문으로 뒤집어 넓혔다.
이번에는 반대 상황이 나왔다.

산업무역부 식품 이력추적 통칙(`11/2026/TT-BCT` → `31/2026/TT-BCT`)은
`sản phẩm, hàng hóa có mức độ rủi ro cao thuộc phạm vi quản lý của Bộ Công Thương`,
**산업무역부 소관 고위험 품목**에만 걸린다. 소스·장류·조미김이 그 목록에 드는지는
부속서를 봐야 아는데 원문 PDF 두 건이 스캔이라 열지 못했다.
베트남 식품 관할은 보건부·산업무역부·농업부로 갈리고 소스류의 소관이 갈린다.

**뺐다.** 이 통칙에는 실재 기한(생산시설 2026-12-01 · 수입시설 2027-03-01)이 붙어 있어
넣었으면 이 조합에 없던 D-Day가 생겼을 것이다. 화면은 좋아지지만,
그 날짜가 우리 제품의 날짜인지 모르는 채로 넣으면 §91이 폐기한 것과 같은 거짓말이다.

**규칙**: 원문이 범위를 좁게 말하면 넓히지 말고, 원문을 못 열었으면 넓게 넣지 않는다.
어느 쪽이든 **원문이 기준이지 화면 사정이 기준이 아니다.**

## 99. `DECREE 15/2018` — 액션 0건이던 법령에 액션을 붙였다

시드는 `actionIds: []`에 `riskLevel: low`, 제목이 "자가공표 절차 (현행 유지)"였다.

그런데 `46/2026`이 보류된 지금 **이 시행령이 베트남에 식품을 넣는 유일한 경로**다.
자가공표를 마치지 않으면 통관 자체가 안 된다. 보류돼서 지금 할 일이 없는 `46/2026`이
`medium`인데 실제로 밟아야 하는 절차가 `low`인 것은 앞뒤가 맞지 않았다.

`medium`으로 올리고 액션 2건(자가공표 서류 작성 · 등록공표 대상 판정)을 붙였다.
제목도 "(현행 유지)"에서 **"46/2026 보류로 이것이 유일한 경로다"**로 바꿨다 —
현행 유지는 법령의 상태이고, 사용자가 알아야 하는 것은 그래서 뭘 해야 하는가다.

**반대로 `46/2026`의 액션은 0건 그대로 뒀다.** 효력이 정지된 시행령의 액션은
지금 할 일이 아니다(§73). 재시행에 대비한 사전 준비를 적으면 그건 지어낸 일이 된다.

## 101. ⚠ 실제 버그 — S2의 '내 우선순위'가 사용자 우선순위를 읽지 않았다

`lib/derive.ts`의 `matchesPreset`이 **`lib/data`의 시드 상수** `priorities`를 봤다.
사용자가 S4에서 추가한 `neo.priorities`가 아니다.

```ts
// 고치기 전
case '내 우선순위':
  return priorities.some((p) => p.category === law.category);   // 시드 3건 고정
```

`data/priorities.json`은 `labeling` · `safety` · `packaging` 셋뿐이고 **`customs`가 없다.**
`Category` 타입과 `CATEGORY_LABEL`에는 `customs`(`통관·관세`)가 있고 S4가 그것을
`+ 영역 추가`로 제공하는데, **추가해도 S2 목록이 그대로였다.**

**2026-09-06까지 이 버그가 드러나지 않은 이유는 `customs` 법령이 하나도 없었기 때문이다.**
JP-food의 `食品衛生法 第27条`(수입신고)가 첫 `customs` 법령이고, 넣자마자 나왔다.

재현: JP 식품 프로필에서 S4 → `+ 영역 추가` → `통관·관세` 추가.
S4는 `PRIORITIES — 4`, `통관·관세 · 법률 1 · 미완 2`로 갱신되는데
S2는 `내 우선순위`에서 계속 `4건`이었다. `localStorage`에는 4건이 들어 있었다.

**고침**: `visibleLaws`가 사용자 우선순위를 인자로 받는다.

```ts
export function visibleLaws(ds, preset, sort, query, mine: readonly Priority[]): Law[]
```

S2가 `usePriorities()`를 호출해 넘긴다. S4가 이미 그 훅을 쓰고 있어 두 화면이
같은 출처를 본다. `derive.ts`에서 시드 `priorities` 임포트를 뺐다 —
이 함수가 유일한 사용처였다.

검증: 기본 3건 → `4건`, `통관·관세` 추가 → `5건`, `localStorage` 삭제 후 → `4건`.
양방향으로 확인했다.

**`data/priorities.json`에 `customs`를 추가하지 않았다.**
`design/NEO-screens.dc.html`의 S4 아트보드에 우선순위 타일이 **3장**이고
`통관·관세`는 `+ 영역 추가`로 넣는 항목이다. 기본값을 4건으로 만들면 디자인이 어긋난다.
CLAUDE.md가 아트보드를 최종 진실로 둔다 — 데이터가 아니라 코드가 틀렸다.

**규칙**: 타입에 있는데 데이터에 없는 값은 **경로가 죽어 있는 것**이지 없는 것이 아니다.
첫 데이터가 들어가는 순간 그 경로가 처음 실행된다. `Category`의 네 값 중 셋만 쓰이고
있었다는 사실 자체가 신호였다.

## 102. 일본은 1차 출처만으로 채워진다

JP-food 5건이 **전부 `official`** 이다. VN에서는 15건 중 5건이었다.

소비자청(`caa.go.jp`)과 후생노동성(`mhlw.go.jp`)이 소관 규정의 원문 PDF와 해설을
직접 올리고, 지자체(센다이시·후쿠오카시)가 같은 내용을 다시 게시한다.
베트남처럼 로펌·상용 법률DB를 거칠 이유가 없었다.

다만 **원문 PDF에서 텍스트를 뽑는 것은 일본 쪽이 더 어렵다.**
`内閣府令 第34号`(266KB)는 압축 스트림이 2개뿐이고 본문이 이미지였다.
§89의 zlib 추출이 베트남에서 통했던 것은 **HS 코드와 QCVN 번호가 라틴·숫자**여서였는데,
일본 법령은 알맹이가 전부 일본어라 CID 인코딩이 풀려도 쓸 수 없다.

**대신 교차확인의 폭을 늘렸다** — 지자체 2곳 + 전문매체 3곳으로 개정 내용을 확정하고,
`sourceTier: official`은 **URL이 소관 부처의 원문이라는 사실**에만 근거한다(§1-13).
등급은 출처의 신원이지 우리가 그것을 읽어냈는지가 아니다.

## 104. 경과조치가 둘일 때 어느 것을 `deadline`에 넣는가

# 4차 작업 — 2-c (JP-cosmetics · JP-shared)

## 106. 우리에게 걸리지 않는 개정은 `changes`에 넣지 않는다

`化粧品基準`의 가장 최근 개정은 2024-07-12(令和6년 후생노동성고시 제243호)로
**시스테아민염산염을 씻어내는 헤어세트료에 8.63g/100g까지 허용**한 것이다.

넣으면 화면의 WHAT CHANGED에 BEFORE/AFTER 한 쌍이 뜬다. 그런데 기본 제품 넷
(크림·립틴트·클렌징폼·샴푸)에 **헤어세트료가 없다.** 사용자는 자기와 무관한 변경을
"내 법령이 바뀌었다"로 읽는다.

`changes: []`로 두어 WHAT CHANGED 섹션이 사라지게 했다. 기준이 살아 있다는 사실은
`DATA-SOURCES.md`에 남긴다.

**규칙**: `changes[]`는 "이 법령이 개정됐는가"가 아니라 **"우리 제품에 걸리는 것이
바뀌었는가"** 로 채운다. §91이 `deadline`에 세운 기준과 같다 —
날짜든 개정 내용이든 **우리 제품의 것인지 확인한 뒤에 넣는다.**

## 107. HS로 표현할 수 없는 차등이 있다

일본 화장품 규제는 제품을 실제로 가른다. 화장품기준의 배합상한도, 법정색소의
허용범위도 **① 점막에 사용되는 것 ② 점막에 쓰이지 않고 씻어내지 않는 것
③ 씻어내는 것** 으로 갈리고, 기본 제품 넷이 그 셋에 정확히 흩어진다.

| 제품 | HS | 화장품기준·색소 구분 |
|---|---|---|
| 립 틴트 | 3304.10 | 점막 사용 — 가장 좁다 |
| 수분 크림 | 3304.99 | 비점막 · 씻어내지 않음 |
| 클렌징 폼 | 3401.30 | 비점막 · 씻어냄 |
| 샴푸 | 3305.10 | 비점막 · 씻어냄 |

**그런데 `3304`가 립틴트와 크림을 같이 담는다.** 씻어내는지 여부는 어느 HS 자릿수에도
나타나지 않는다. `hsPrefixes`를 6자리(`330410`)로 내려도 ②와 ③을 가를 수 없다.

`hsPrefixes`를 전부 화장품 전 범위로 두고 **차등을 액션 문구에 넣었다** —
`점막용·씻어내는 제품은 상한이 다르다`, `립 제품의 색소를 점막 사용 가능 범위로 좁혀 재확인`.

§83은 "차등을 만들 근거가 없었다"였다. 여기는 다르다 — **근거는 있는데 그릇이 없다.**
`hsPrefixes`가 표현할 수 있는 것은 관세분류이지 사용 부위가 아니다.
그릇에 맞추려고 없는 구분을 만드는 것이 규칙 1 위반이므로 만들지 않았다.

## 108. 의무자가 수입자여도 자료가 수출자에게서 나오면 넣는다 — 두 번째 사례

`容器包装リサイクル法`의 `特定事業者`는 **일본에 거점이 있는 사업자**다.
일본용기포장리사이클협회가 명시한다 — 해외 제조자는 대상이 아니고,
용기포장을 붙인 상품을 수입해 파는 일본 사업자가 재상품화 의무를 진다.

VN `DECREE 110/2026`(EPR)과 같은 구조다. 그때 세운 기준을 그대로 적용했다 —
**의무자가 누구인지가 아니라 자료가 어디서 나오는지를 본다.** 수입자가 의무량을
산정하려면 재질별 포장 중량표가 필요하고 그건 수출자만 만들 수 있다.

다만 **화면이 그 사실을 숨기지 않게 했다.** `title`이
`재상품화 의무 — 의무자는 일본 수입자지만 자료는 수출자가 낸다`이다.
"당신의 의무"라고 쓰면 거짓말이고, 빼면 실무에서 실제로 요구받는 자료를 놓친다.

같은 공용 파일의 `資源有効利用促進法`(식별표시)은 반대다 — 프라마크·종이마크를
**포장 도안에 인쇄**해야 하므로 한국에서 인쇄판을 만들 때 들어간다. 수출자가 직접 한다.
그래서 `HIGH`이고 EPR 쪽이 `MEDIUM`이다.

## 109. `meti.go.jp`는 기본 User-Agent를 막는다

출처 URL 생사 확인을 `curl`로 돌리다 `www.meti.go.jp`에서 **403**을 받았다.
URL이 죽은 것이 아니라 경제산업성이 기본 UA를 거부한다. 브라우저 UA를 붙이면 200이다.

```bash
curl -s -o /dev/null -w '%{http_code}' -L -A "Mozilla/5.0 …" <url>
```

**403을 링크 오류로 읽고 출처를 갈아치우면 1차 출처를 2차로 떨어뜨리게 된다.**
URL 검증에서 4xx가 나오면 UA를 바꿔 한 번 더 본다.

## 113. 시행일이 오래된 것은 숨길 일이 아니다

JP-electronics 네 건의 `effectiveDate`가 2001 · 1999 · 1962 · **1950**이다.
화면에 `1950.06.01 시행`이 뜬다.

처음에는 어색해 보였지만 그대로 뒀다. `changes: []`와 함께 읽히면
**"최근에 바뀐 것"이 아니라 "원래부터 지켜야 하는 것"** 이라는 뜻이 되고,
그게 정확한 상태다. 전파법 기적 제도는 실제로 오래된 규정이고,
한국 수출자가 놓치는 이유는 바뀌어서가 아니라 몰라서다.

날짜를 최근으로 당기려면 개정 이력 중 하나를 골라야 하는데, 그건 §71이 폐기한
"화면을 좋게 만들려고 날짜를 고르는 일"과 같은 종류가 된다.

**예외를 둔 곳**: `食品衛生法 第12条`·`第27条`는 2020-06-01을 썼다(§103).
1947년 제정일은 **지금의 조문 번호 체계가 아니기 때문**이다 — 날짜를 당긴 것이 아니라
`第12条`라는 표기가 성립한 날을 적은 것이다.

# 4차 작업 — 2-e (US-food)

## 115. `originScope`가 처음 실행됐다 — 그리고 예상과 다른 데서 나왔다

3차 지시서는 `originScope`가 **미국 식품의 FSVP·시설등록**에서 나올 것으로 봤다.
**둘 다 아니었다.** FSVP도 FDA 시설등록도 출발국을 가리지 않는다 —
미국 밖 어느 나라에서 오든 똑같이 걸린다.

실제로 나온 것은 **한미 FTA 원산지증명**이다. 특혜관세는 협정 상대국에서 출발한
물품에만 성립하므로 `originScope: ["KR"]`이 정확히 이 경우다.

**규칙**: `originScope`는 "해외 사업자에게만 걸리는가"가 아니라
**"이 출발국에서 온 물품에만 걸리는가"** 다. 앞의 것은 우리 데이터에서 항상 참이라
필드가 필요 없다(도착국이 곧 규제국이고 사용자는 늘 해외 수출자다).
뒤의 것은 **FTA·상호인정협정·국가별 Import Alert** 셋에서만 나온다.

검증 — §69가 만든 경로가 처음 실행됐다.

| 프로필 출발국 | S2 | 하단 |
|---|---|---|
| KR → US | 6건 | 없음 |
| JP → US | 5건 | `출발국 KR 외에는 수출국별 요건 데이터가 아직 없습니다` |

## 116. `dueDate`가 `null`이 아닌 첫 액션

§71이 허구 D-Day를 폐기한 뒤 **모든 액션의 `dueDate`가 `null`이었다.**
`US-a-225-01`(FDA 시설등록 갱신)에 `2026-12-31`을 넣었다.

넣을 수 있었던 이유는 하나다 — **그 날짜가 액션 자체의 마감이기 때문이다.**
FDA 갱신 창구는 10월 1일에 열려 12월 31일 23:59에 닫히고, 그때까지 갱신하지 않으면
등록이 소멸한다. 법령의 기한이 아니라 **이 행동의 기한**이다.

다른 액션에는 여전히 `dueDate`가 없다. "라벨을 고쳐라"에는 법이 정한 날짜가 없다.
법령의 `deadline`을 액션에 복사하면 §71이 폐기한 역산이 다시 생긴다.

## 117. `fda.gov`는 루트조차 `curl`에 404를 준다

§109가 `meti.go.jp`의 403을 기록했는데 FDA는 더 심하다 —
`https://www.fda.gov/` 자체가 404를 돌려준다. 브라우저 UA를 붙여도 같다.

```
404  https://www.fda.gov/
404  https://www.fda.gov/food/... (실재하는 페이지)
200  https://www.ecfr.gov/...
200  https://www.cbp.gov/...
```

**URL 생사 확인을 `curl` 하나로 돌리면 FDA 출처를 전부 죽은 링크로 오판한다.**
WebFetch는 같은 URL을 정상적으로 읽는다. 실제로 잘못 찍었던 URL 하나
(`/food/importing-food-products-united-states/prior-notice-imported-foods`)는
WebFetch에서도 404가 나와 올바른 경로(`/industry/fda-import-process/prior-notice-imported-foods`)로
고쳤다 — **도구를 바꿔 보면 진짜 404와 봇 차단이 갈린다.**

| 도메인 | curl | 대응 |
|---|---|---|
| `meti.go.jp` | 403 (기본 UA) | 브라우저 UA를 붙인다 |
| `fda.gov` | 404 (UA 무관) | WebFetch로 확인한다 |
| `vfa.gov.vn` | `ECONNREFUSED` | 서버가 실제로 죽어 있다 |

## 118. 제외한 것에도 D-Day가 있었다 — 그래서 더 조심했다

이 조합에서 뺀 셋에 전부 그럴듯한 날짜가 붙어 있었다.

| 제외한 것 | 붙어 있던 날짜 | 뺀 이유 |
|---|---|---|
| FSMA 204 이력추적 | 2028-07-20 | **FTL에 우리 제품이 없다** |
| `"healthy"` 표시 규칙 | 2028-02-25 | **쓰겠다고 정한 제품에만 걸린다** |
| 전면 표시(FOP) | 최종규칙 후 3~4년 | **아직 제안규칙이다** |

세 날짜 다 넣었으면 화면에 D-Day가 셋 더 떴을 것이다. 그런데
첫째는 **우리 제품의 날짜가 아니고**(§91), 둘째는 **의무가 아니라 선택이고**,
셋째는 **아직 법이 아니다**.

§71이 "없는 날짜를 지어내지 마라", §91이 "있는 날짜를 엉뚱한 제품에 붙이지 마라"였다면
여기에 하나가 더 붙는다 — **선택적 표시의 준수일을 전 제품의 마감처럼 쓰지 마라.**

# 4차 작업 — 2-f (US-cosmetics · US-shared)

## 120. ⚠ 또 같은 누락 — `KORUS FTA`를 조합 파일에 넣었다

2-e에서 한미 FTA 원산지증명(`US-2012-010`)을 `US-food.json`에 넣었다.
**틀렸다.** 특혜관세는 품목을 가리지 않는다 — 화장품도 전기전자도 받는다.
US-화장품을 조사하다 같은 법령이 또 필요해지면서 드러났다.

§82(라벨 시행령)·§92(EPR)와 **세 번째로 같은 실수**다. 공용 파일 제도가 생긴 뒤에도
반복됐다는 것이 문제다. `US-shared.json`으로 옮기고 `itemCategories`를 세 품목,
`hsPrefixes`를 `[]`로 바꿨다(§86). 액션 id는 그대로 뒀다(§15 · §52).

**왜 또 놓쳤나**: 조합 하나를 끝내고 다음으로 넘어가는 순서 때문이다.
US-food를 할 때는 식품 관점에서만 봤고, "이게 화장품에도 걸리나"를 묻지 않았다.

**규칙**: 조합 파일에 법령을 넣기 전에 **"이 법령의 조문이 품목을 지명하는가"** 를 묻는다.
- 지명한다(`電気がま`·`ジャー炊飯器`·`FTL`) → 조합 파일
- 지명하지 않는다(FTA·원산지 표시·강제노동·포장재) → **공용 파일**

`customs` 카테고리 법령은 **거의 전부 공용**이다. 통관은 물건이 무엇이든 거친다.
지금까지 넣은 `customs` 법령 넷 중 조합 전용이 맞는 것은
`食品衛生法 第27条`(식품위생법 소관 식품만)과 `21 CFR 1 Subpart I`(FDA 규제 식품만)
둘뿐이고, 나머지 둘(KORUS · UFLPA)은 공용이었다.

## 121. 갱신 주기가 회사마다 다르면 `deadline`을 넣을 수 없다

`MoCRA §607`의 시설등록 갱신은 2년 주기인데 **기준일이 그 시설의 최초 등록일**이다.
FDA 예시가 그대로다 — `registration on February 20, 2024 requires renewal by
February 20, 2026`.

FDA 식품시설 등록(`21 CFR 1 Subpart H`)과 정반대다. 그쪽은 **모든 시설이 같은 창구**
(짝수 해 10.01~12.31)를 쓰므로 `2026-12-31`이 누구에게나 참이다.
MoCRA는 사용자마다 다르므로 **어떤 날짜를 넣어도 남의 날짜**가 된다.

`deadline: null`로 두고 `transitionNote`에 규칙을 적었다. 액션은 "갱신일을 확인하라"다.

**규칙**: `deadline`은 **이 데이터를 보는 모든 사용자에게 같은 날**일 때만 넣는다.
사용자 고유의 날짜는 데이터가 아니라 **사용자가 채워야 할 값**이다.

## 122. 화장품은 두 나라 모두에서 HS 차등이 성립하지 않았다

| 조합 | HS 차등 | 실제 차등의 축 |
|---|---|---|
| VN-화장품 | 없음 | 없음 (§83 — 근거 자체가 없었다) |
| JP-화장품 | 없음 | 점막 / 씻어냄 (§107 — 그릇이 없다) |
| US-화장품 | 없음 | 점막 접촉 · 눈가/립 사용 |

우연이 아니다. **화장품 규제는 「어디에 바르는가」로 갈리는데 HS 분류는 「무엇인가」로 갈린다.**
`3304`가 립 틴트(3304.10)와 수분 크림(3304.99)을 같이 담는 이상,
`hsPrefixes`로는 MoCRA의 점막 면제 예외도 색소의 눈가 제한도 표현할 수 없다.

반대로 전기전자는 두 나라 모두에서 갈렸다(§90 · §112). 법령이 `電気がま`·`8516.60.10`처럼
**제품명·HS 코드로 대상을 못 박기 때문**이다.

**결론**: HS 차등의 유무는 조사의 깊이가 아니라 **그 품목 규제가 대상을 지정하는 방식**에
달렸다. 화장품 조합에서 차등이 안 나오는 것은 조사를 덜 한 것이 아니다.

## 123. 법은 있는데 규칙이 없는 상태

MoCRA는 FDA에 하위규칙 셋을 위임했는데 **2026-09-06 현재 셋 다 없다.**

| 위임 규칙 | 상태 |

## 125. 같은 규제를 한 나라에서는 빼고 다른 나라에서는 넣었다

리튬전지 운송 요건을 **JP-electronics에서는 뺐고 US-electronics에서는 넣었다.**
모순처럼 보이지만 근거가 다르다.

| | 일본 | 미국 |
|---|---|---|
| 확보한 근거 | 물류업체 블로그 · 공사(公社) 안내 | **PHMSA 원문 + eCFR 조문** |
| 법의 성격 | IMDG·IATA 국제 기준을 국내법이 받는 구조 | `49 CFR`이 **미국 상거래 내 운송을 직접 규율** |
| 의무의 위치 | 선적 단계 — 출발국·경유지 규정이 함께 걸린다 | 조문이 **후속 유통자**에게 시험요약서 의무를 지운다 |

**규칙**: 같은 주제라도 **그 나라 법령이 직접 의무를 지우는지**를 보고 판단한다.
"국제 기준이니 어디나 같다"로 뭉치면 한쪽에서는 없는 의무를 만들고
다른 쪽에서는 있는 의무를 빠뜨린다.

## 126. 법이 아닌 것을 법으로 적지 않는다 — UL

미국에는 일반 소비자 가전에 대한 **연방 강제 안전인증이 없다.**
일본 조합을 먼저 한 뒤라 이 공백이 눈에 띄었다 — 일본은 밥솥·LED·보조배터리가
전부 `電気用品安全法` 대상인데 미국에는 대응물이 없다.

UL 마크는 소매체인·보험사·주 전기규정이 요구하는 것이지 연방법이 요구하는 것이 아니다.
**실무상 UL 없이는 대형 유통에 못 들어가지만, 그건 시장의 요구다.**

넣고 싶은 유혹이 있었다. 넣으면 화면이 충실해 보이고 사용자에게도 유용하다.
그런데 이 앱은 **법령이 바뀌면 당신이 뭘 해야 하는가**를 판다. 시장 관행을 법령 행으로
적으면 그 명제가 무너진다. 뺐고, 사실 자체는 `DATA-SOURCES.md`에 남겼다.

## 127. 봇 차단이 세 번째 형태로 나왔다

§109(`meti.go.jp` 403) · §117(`fda.gov` 404)에 이어 **eCFR**이 나왔다.

```
curl   https://www.ecfr.gov/...   → 200   (살아 있다)
WebFetch https://www.ecfr.gov/... → 302 → unblock.federalregister.gov  (내용을 못 읽는다)
```

**curl로는 살아 있고 WebFetch로는 못 읽는다.** `fda.gov`과 정반대다.
그래서 `49 CFR 173.185`의 리튬전지 마크 경과 규정(구 마크를 2026-12-31까지 허용)을
2차 요약 한 곳에서만 보고 **데이터에 넣지 못했다.** 사실이라면 실기한이 하나 더 생긴다.

| 도메인 | curl | WebFetch |
|---|---|---|
| `meti.go.jp` | 403 (UA 교체로 해결) | 정상 |
| `fda.gov` | 404 (해결 불가) | **정상** |
| `ecfr.gov` | **200** | 302 리다이렉트 (해결 불가) |
| `vfa.gov.vn` | ECONNREFUSED | ECONNREFUSED (실제로 죽었다) |

**규칙**: 출처를 확인할 때 도구 하나로 판정하지 않는다.
`curl`과 WebFetch가 서로를 보완하고, 둘 다 막히면 그 사실을 기록하고 넘어간다.
**못 읽은 것을 읽은 척 적는 것이 유일하게 하면 안 되는 일이다.**

## 128. HS 차등의 갈래가 나라마다 다른 이유

전기전자에서 두 번째로 차등이 실재했다. 그런데 **모양이 다르다.**

| | 일본 | 미국 |
|---|---|---|
| 갈래 | `제품 3 / 2 / 1 / 1` | `제품 4 / 1 / 2 / 4` |
| 이유 | 법령마다 **대상 품목 목록**이 있다 (`電気がま`·`ジャー炊飯器`) | 규제 **축**이 다르다 (전파·효율·운송·안전) |

일본은 한 법이 "이 품목들"을 열거하므로 목록에 있느냐로 갈린다.
미국은 각 기관이 자기 축으로 전 품목을 훑으므로, 그 축에 걸리는 제품만 남는다.

**같은 `hsPrefixes` 필드가 두 가지 다른 현실을 담는다.** 어느 쪽이든
"이 법령이 내 제품에 걸리는가"에는 정확히 답한다 — 그게 이 필드의 일이다.

## 135. 2차 출처가 기한의 **성격**을 바꿔 놓았다

`PerBPOM 25/2025`의 경과 기한을 두고 2차 출처 하나는 이렇게 썼다.

> BPOM이 `e-Notifikasi Kosmetik`이라는 새 디지털 시스템을 도입했고,
> **2026년 10월 3일부터 모든 사업자가 이 시스템을 써야 한다.**

날짜는 맞았다. 그런데 **무엇의 기한인지가 틀렸다.** 원문 제15조는 이렇다.

```
Pasal 15
Pelaku Usaha yang telah memiliki nomor notifikasi Kosmetik sebelum berlakunya
Peraturan Badan ini, harus menyesuaikan dengan ketentuan dalam Peraturan Badan ini
paling lama 12 (dua belas) bulan terhitung sejak Peraturan Badan ini diundangkan.
```

시스템 전환이 아니라 **원료 기준 적합**의 기한이다. 해야 하는 일이 완전히 다르다 —
계정을 옮기는 것과 **처방을 352쪽 부속서와 대조해 필요하면 배합을 바꾸는 것**이다.

§89는 2차 출처가 **적용 범위**를 좁게 옮긴 사례였다. 여기서는 **의무의 내용**이 바뀌었다.
날짜가 같아서 대조하지 않았으면 넘어갔을 것이다.

**규칙**: 날짜가 맞는다고 그 날짜가 무엇의 기한인지까지 맞는 것은 아니다.
`deadline`을 넣을 때는 **날짜와 함께 그 날까지 무엇을 해야 하는지를 원문에서 확인**한다.
그 둘이 액션 제목이 되기 때문이다.

## 139. 인증기관은 범위를 넓게 쓴다 — §89의 세 번째 형태

인도네시아 인증기관(LSPro)들의 자료가 **"LED 램프와 루미네어는 SNI 의무 대상"** 이라고
쓴다. 여러 곳이 같은 말을 한다.

**틀렸다.** 국가표준화청(BSN)과 조명공업협회 자료를 보면 **LED 램프 의무 SNI는 아직
시행되지 않았다.** 산업부가 기술 성숙도·시험 인프라를 이유로 미뤘고,
램프제조협회(Gamatrindo)가 연기를 건의했다. 2001~2002년 `lampu swaballast` 의무 SNI는
형광등 계열이지 LED가 아니다.

§89(베트남)에서는 **컴플라이언스 매체 셋이 범위를 좁게** 옮겼다. 자기 독자에 맞춰 잘랐다.
§135(인도네시아 화장품)에서는 **2차 출처가 기한의 성격을 바꿨다.**
여기서는 **인증기관이 범위를 넓게** 썼다 — 자기 사업 대상이기 때문이다.

**규칙**: 2차 출처의 편향은 방향이 정해져 있지 않다. **누가 썼는가를 보고 어느 쪽으로
기울지 예상한다.**

| 출처 유형 | 기우는 방향 |
|---|---|
| 업계 전문매체 | 자기 독자 품목으로 **좁힌다** (§89) |
| 인증·시험기관 | 자기 서비스 대상으로 **넓힌다** (§139) |
| 컨설팅·법무 블로그 | 최신 화제로 **성격을 바꾼다** (§135) |

`Permendag 21/2025`의 부속서가 8516 안에서 항목을 골라 지정한다 —
`8516.60.10 Rice cooker`는 있고 다리미·전기주전자는 다른 조건이다.
4자리 `8516`으로 두면 사용자가 추가한 다른 8516 제품까지 대상으로 보인다.

**`hsPrefixes: ["851660", "853952"]`** 로 적었다.
`productsMatching`이 `p.hsCode.replace(/\D/g,'')`로 숫자만 남겨 `startsWith`를 하므로
`"8516.60"` → `"851660"`이 그대로 걸린다. `check-data.mjs`도 통과한다 —
`"851660".startsWith("8516")`이 참이라 품목 범위 안이다.

지금까지 `hsPrefixes`는 2자리(식품 `16`~`22`)와 4자리(`8507` · `2103`)만 썼다.
**법령이 소호(6자리)까지 지정하면 그 정밀도를 그대로 쓴다** —
필드가 이미 그것을 지원하고 있었다.

# 4차 작업 — B7-1 · B7-3 (화면 반영)

## 144. ⚠ 지구본 색 불일치는 사고가 아니라 아트보드의 지정이었다

4차 지시서 B7-1은 "두 화면이 다른 색으로 렌더된다. 판단 근거가 기록되지 않았다"며
**한 값으로 통일**하라고 했다. 아트보드를 열어 보니 전제가 틀렸다.

```html
<!-- design/NEO-screens.dc.html:50  S1 -->
<x-import ... mode="globe" ...>                    ← dot-color 없음
<!-- design/NEO-screens.dc.html:610 S5 -->
<x-import ... mode="asia" dot-color="#3A3A3A" ...> ← 명시 지정
```

`design/neo-dots.js:37`의 컴포넌트 기본값이 `#6B6B6B`다.
**아트보드는 S5에만 어두운 값을 덮어썼다.** 지금 코드는 그걸 정확히 재현하고 있었다 —
S1은 `dotColor`를 안 넘겨 기본값을, S5는 `var(--geo-dot)`을 쓴다.

CLAUDE.md가 `design/NEO-screens.dc.html`을 **최종 진실로, 문서보다 우선**한다고 정한다.
**통일하지 않았다.**

### 왜 달라야 하는지 — 실측으로 확인했다

`--geo-dot`을 `#6B6B6B`로 바꾸고 S5를 렌더했다.

**`TH · 지원 예정` 라벨이 지형에 묻힌다.** 라벨 글자색이 `--text-3` = **#6B6B6B**로
지형 점과 정확히 같은 색이기 때문이다. `CN · 지원 예정`도 바탕을 잃고,
미지원 국가 마커(회색 사각형)가 지형 점과 구분되지 않는다.

| | 배경 #171717 대비 | 위에 얹히는 것 |
|---|---|---|
| S1 지구본 `#6B6B6B` | 3.37:1 | 흰 항로 + 빨간 도착 마커. **라벨 없음** |
| S5 지도 `#3A3A3A` | 1.58:1 | 항로 + 마커 + **`--text-3` 라벨** |

**S5의 지형은 `--text-3` 아래로 내려가야 한다. 그 화면의 라벨이 `--text-3`이기 때문이다.**
S1에는 라벨이 없어 그럴 이유가 없고, 지구본은 히어로 비주얼이라 밝은 편이 낫다.

### 고친 것 — 값이 아니라 **의도의 가시성**

색은 그대로 두고, **암묵적 기본값에 기대던 것을 명시로 바꿨다.**
S1이 아무것도 안 넘겨서 색이 정해지는 구조가 이걸 사고처럼 보이게 만든 원인이다.

```css
/* 지오그래피 — 두 화면이 다른 값을 쓴다. 아트보드가 그렇게 지정했고 이유가 있다. */
--geo-dot:       #3A3A3A;   /* S5 지도. --text-3 아래로 내린다 */
--geo-dot-globe: #6B6B6B;   /* S1 지구본. neo-dots.js 원본 기본값이다 */
```

- `app/page.tsx` — `dotColor="var(--geo-dot-globe)"` 명시
- `app/map/page.tsx` — `var(--geo-dot)` 그대로
- `components/DotGeo.tsx` — 기본값을 `var(--text-3)`에서 `var(--geo-dot)`로.
  글자 토큰에 지형 색을 매어 두는 것이 애초에 잘못이었다. 기본값은 **어두운 쪽**이다 —
  라벨을 얹는 화면에서 안전한 쪽이기 때문이다
- `app/kitchen-sink/page.tsx` — 두 값을 나란히 보는 자리라 화면과 같은 색을 넘긴다

**렌더 결과는 이전과 픽셀 단위로 같다.** 바뀐 것은 다음 사람이 이걸 다시 "고치려" 하지
않는다는 것뿐이다.

**규칙**: 두 호출부가 다른 값을 쓰는데 한쪽이 **기본값에 기대고 있으면**,
그건 결정이 아니라 사고로 읽힌다. **값이 다른 것 자체가 결정이라면 양쪽 다 명시한다.**

## 145. B7-3 — 죽은 컨트롤 넷 중 둘을 지우고 둘을 살렸다

사용자 확정: **`국가 검색`과 `저장`만 구현한다.**

### 지운 것

| 위치 | 컨트롤 | 지운 이유 |
|---|---|---|
| S4 우상단 | `설정` | 열 화면이 없다. PRD에 설정 IA가 정의돼 있지 않다 |
| S4 하단 | `맞춤 분석 다시 실행` | **재실행할 분석이 없다.** 화면은 프로필이 바뀌면 이미 즉시 따라간다 |

두 번째가 특히 나빴다 — 없는 계산을 있는 것처럼 보이게 하는 링크였다.
누르면 "다시 계산했다"고 믿게 되는데 실제로는 아무 일도 일어나지 않는다.

### 살린 것 1 — `저장`

`lib/useLawsSaved.ts`를 `createIdSetStore('neo.laws.saved')`로 만들었다.
`neo.actions.done` · `neo.notifications.read`와 같은 스토어다(§persistentIdSet).

**완료 표시와 다르게 조합이 바뀌어도 비우지 않는다.** 완료는 그 조합에서 실제로 한
일이라 조합이 바뀌면 의미가 없어지지만, 저장은 "이 법령을 다시 보겠다"는 표시라
도착국을 바꿨다 돌아와도 남아 있어야 한다. 법령 id가 전역에서 유일해 충돌하지 않는다.

`app/laws/[id]/SaveToggle.tsx`는 페이지가 서버 컴포넌트라 떼어낸 다섯 번째 클라이언트
조각이다(§61). **상태를 색으로만 말한다** — 저장되면 `--accent`, 아니면 `--text-3`.
아이콘이나 채워진 별을 쓰지 않는다. 이 앱에 아이콘이 없고, 글자가 색으로 상태를
말하는 것이 다른 라벨과 같은 어법이다. 터치 타겟은 `minHeight: 44`다.

**S2에 `저장됨` 필터를 붙였다.** 저장만 만들고 볼 자리를 안 만들면 반쪽이다.
`FILTER_PRESETS` 맨 뒤에 둔다 — 앞의 넷은 데이터가 정하는 묶음이고
이것만 사용자가 만든 묶음이다.

빈 상태 문구를 따로 준다. 나머지 필터의 0건은 "조건을 좁혀서"이지만
`저장됨`의 0건은 "아직 아무것도 저장하지 않아서"라 원인이 다르다 —
`저장한 법률이 없습니다. 법률 상세 우상단에서 저장합니다`.

### 살린 것 2 — `국가 검색`

**비기능이었던 이유가 사라졌다.** 코드 주석이 "지원 국가가 VN 하나뿐이라 거를 것이
없다"였는데 B6로 **넷이 됐고 마커는 열셋이다.** §101(`customs` 필터 버그)과 같은 구조다 —
**데이터가 없어서 죽어 있던 경로가 데이터가 차면서 살아난다.**

검색은 **마커만 거른다. 지도와 항로는 그대로 둔다** — 검색으로 지형이 사라지면
어디를 보고 있는지 알 수 없다.

판정은 **코드·한국어명·영문명 셋 다** 본다(`VN` / `베트남` / `Viet Nam`).
지도에 보이는 것은 코드뿐이지만 사용자 머리에 있는 것은 한국어 이름이다.

**구현 주의**: `markers` 배열 자체를 줄이지 않고 **렌더 시점에 거른다.**
좌표(`points`)를 `DotGeo`가 `markers` 순서대로 주기 때문에 배열을 줄이면
인덱스가 어긋나 마커가 엉뚱한 자리에 붙는다.
